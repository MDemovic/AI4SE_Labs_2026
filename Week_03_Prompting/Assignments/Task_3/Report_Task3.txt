Task 3 – Name-based result metric

I chose name-based multiset F1 as an additional metric because exact-result accuracy gives no partial credit. It compares restaurant names while preserving duplicate counts. 
F1 gives partial credit and accounts for both missing and extra results, which is useful because questions can return multiple restaurants.

For each question, I execute the generated SQL against a SQLite database reconstructed from the supplied files and compare its restaurant names with the expected names.
- Names are compared exactly as stored, without fuzzy matching or changing letter case. 
- Duplicate names are counted rather than removed. For each name, the number of matches is the smaller of its expected and predicted counts.

--- Metric ---
TP = total number of matched name occurrences
FP = number of predicted name occurrences minus TP
FN = number of expected name occurrences minus TP

Precision = TP / (TP + FP)
Recall = TP / (TP + FN)
F1 = 2 * TP / (2 * TP + FP + FN)

For example, if the expected names are [A, B, C] and the predicted names are [A, B, D, E], there are two matches, two extra names, and one missing name. Precision is 2/4, recall is 2/3, and F1 is 4/7, or about 57.14%.
- When both results are empty, precision, recall, and F1 are defined as 1. 
- When only one is empty, they are defined as 0. A query that fails execution receives 0, even if its expected result is empty.

The final score is macro F1: the average of the per-question F1 scores. Each question has equal weight, so questions returning many restaurants do not dominate the comparison.
I also report exact-match name accuracy, along the F1


--- Implementation ---
evaluate_name_metrics.py = It loads the existing Task 2 prediction files and uses the supplied evaluator’s database-loading function.
It reads expected results only during evaluation and does not change the predictions or labels.
For nonempty predictions, the script extracts the NAME column. House numbers and any additional output columns are ignored by the name metric. 
Invalid nonempty outputs without a NAME column receive 0 and are recorded as errors. 
Empty results are compared as empty multisets, matching the original evaluator's approach.

Run from the repository root:
python Week_03_Prompting/Assignments/Task_3/evaluate_name_metrics.py

Output:
- name_metrics_summary.csv: metric values for each framework.
- name_metrics_per_question.csv: scores, result counts, and errors for each question.


--- Results ---
These results use the corrected Task 2 runs, which return HOUSE_NUMBER and NAME.
Before correcting the prompts, the original accuracy was 27.74% and name-based F1 was 98.49%. After requesting HOUSE_NUMBER and NAME with the required join, these increased to 94.84% and 98.51%. The large accuracy increase mainly reflects the corrected output columns. Name-based F1 changed only slightly because it ignores the numerical column, although the required join also changed some returned rows.
Framework    Original accuracy    Name exact match    Macro name F1
ICIO         94.84% (147/155)     94.84% (147/155)    98.51%
ReAct        94.84% (147/155)     94.84% (147/155)    98.51%
SCOPE        94.84% (147/155)     94.84% (147/155)    98.51%

All three frameworks had the same scores because their returned result were identical for all 155 questions, even tho their SQL wordings were different. 
For each framework, 8 questions did not match the complete expected name multiset. The higher F1 score shows that these mismatches often had substantial overlap rather than being completely wrong.
There are 43 questions with empty expected results, like we saw in the task before. I also calculated macro F1 over the 112 questions with nonempty expected results, which was 97.94% for all three frameworks.
This metric complements the original accuracy; it does not replace it. The original metric checks complete returned rows containing HOUSE_NUMBER and NAME. Name-based F1 measures partial overlap in the returned names, but does not check whether house numbers are correct.

Different restaurants can share a name, so matching names does not prove that the correct restaurant identities were retrieved. In these runs, name-only exact accuracy equals the original accuracy, but F1 still shows partial overlap on questions that fail exact matching. The metric also ignores address fields and other output columns. 
Empty results can match even when the query selects inappropriate columns. Finally, it still relies on the expected names being correct.
